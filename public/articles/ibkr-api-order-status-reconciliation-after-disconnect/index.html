IBKR API Order Status Reconciliation After a Disconnect

A reconnected client starts with an empty picture of the account, not a corrected one. Everything that happened during the gap has to be re-read from the broker before the strategy is allowed to send another order.

Technical engineeringNo custodySource handoffRemote collaboration

After an IBKR disconnect, rebuild state from working orders, terminal orders and executions, compare positions per instrument, and keep routing paused while any order is still unknown.

A reconnect does not replay what you missed

The TWS API delivers order status and execution callbacks over a live socket. Events that fire while the client is disconnected are not queued for later delivery, so silence after a reconnect proves nothing. Treat the broker as the source of truth and rebuild state explicitly instead of trusting the last local snapshot.

  • Silence after a reconnect is not evidence that nothing filled.
  • Rebuild from broker requests, not from the last known local state.
  • Keep routing paused until the rebuild finishes and matches.

Rebuild from working orders, terminal orders and executions

IBKR exposes separate requests for orders that are still working, orders that reached a terminal state and fills that already happened. Each answers a different question, so a reconciliation built on only one of them will miss a case. Client identity also matters: orders are associated with the client that placed them, and the available requests differ in whether they return orders from every client or only the current one.

  • Read working orders, terminal orders and executions separately, then merge them by the broker's permanent identifier.
  • Record which client placed each order so a restarted process can claim its own working orders.
  • Executions and commission reports are only returned for a recent window, so persist them locally as they arrive.

Resolve differences before the strategy resumes

Reconciliation should end in a decision, not a report. Every local order must land in one of a small set of states: confirmed filled, confirmed working, confirmed cancelled or unknown. Unknown is the only state that must block trading, because that is where a duplicate order or an unhedged position gets created.

  • Compare position quantity per instrument, not only order-by-order status.
  • Send unknown orders to an operator alert with the order reference and the last known local state.
  • Log the reconciliation result with a timestamp so the audit trail explains why routing resumed.

Reconnect reconciliation checklist

  • The client re-requests a valid next order identifier before sending any new order.
  • Working orders, terminal orders and executions are all re-read after a reconnect.
  • Local order records store the broker's permanent identifiers, not only local ones.
  • Position quantities are compared against the account, instrument by instrument.
  • Routing stays paused while any order is unknown, and an operator is alerted.
